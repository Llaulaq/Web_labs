## Задание 1: Анализ HTTP-запроса

Дан запрос:
```
POST /api/users HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 45
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9

{"name": "John Doe", "email": "john@example.com", "age": 30}
```

1. **Метод:** `POST` — создание нового ресурса на сервере.
2. **Ресурс:** `/api/users` — коллекция пользователей.
3. **Заголовки:**
   - `Host: api.example.com` — имя хоста, к которому обращаются (обязателен в HTTP/1.1);
   - `Content-Type: application/json` — формат тела запроса;
   - `Content-Length: 45` — длина тела в байтах;
   - `Authorization: Bearer <токен>` — данные для аутентификации (JWT-токен).
4. **В теле:** данные нового пользователя — имя, email, возраст.
5. **Формат:** JSON (`application/json`).

## Задание 2: Выбор статус-кодов

| Операция | Статус-код | Обоснование |
|----------|------------|-------------|
| Успешное получение списка пользователей | 200 | Успешный GET с телом ответа |
| Создание нового пользователя | 201 | Ресурс успешно создан |
| Пользователь не найден по ID | 404 | Ресурса не существует |
| Некорректный email в запросе | 400 | Ошибка в данных запроса со стороны клиента |
| Пользователь уже существует | 409 | Конфликт состояния ресурса (дубликат) |
| Внутренняя ошибка сервера | 500 | Непредвиденная ошибка на сервере |
| Успешное удаление пользователя | 204 | Успех без тела ответа |
| Требуется аутентификация | 401 | Клиент не аутентифицирован |

## Задание 3: DNS и порты

1. **`https://example.com:8080`** — браузер запросит у DNS IP-адрес `example.com`, затем подключится к этому IP на порт **8080** (явно указан, вместо стандартного 443) по HTTPS.
2. **Порт 80** — стандартный порт HTTP; **порт 443** — стандартный порт HTTPS (шифрованное соединение TLS).
3. **`localhost`** — имя, обозначающее «этот же компьютер», соответствует IP **127.0.0.1** (IPv4) и `::1` (IPv6).
4. **DNS** — система доменных имён: переводит человекочитаемые имена (`example.com`) в IP-адреса, к которым обращаются программы.
5. **Кэш DNS** — локальное хранение результатов DNS-запросов на время жизни записи (TTL), чтобы не запрашивать сервер при каждом обращении и ускорить работу.

## Задание 4: Путь запроса

```
[Браузер] → [DNS] → [Балансировщик/Nginx] → [Веб-сервер приложения] → [Приложение (код)] → [База данных]
```

- **Браузер** формирует HTTP-запрос и отправляет его.
- **DNS** преобразует доменное имя в IP-адрес.
- **Nginx / балансировщик** принимает запрос, при необходимости терминирует TLS и распределяет нагрузку (reverse proxy).
- **Веб-сервер приложения** (например, Uvicorn) принимает соединение и передаёт запрос в приложение.
- **Приложение** выполняет бизнес-логику и при необходимости обращается к БД.
- **База данных** хранит и возвращает данные; ответ проходит обратно по той же цепочке.

## Задание 6: Практическая работа с curl

Выполнено:

```bash
curl -v https://httpbin.org/get
curl -v -X POST https://httpbin.org/post -H "Content-Type: application/json" -d '{"name": "John", "age": 30}'
curl -v https://httpbin.org/status/404
curl -v https://httpbin.org/status/500
```

Анализ вывода `curl -v`:
- Строки с `>` — заголовки **запроса**, отправленные клиентом;
- `< HTTP/1.1 200 OK` — **статус-код** ответа;
- Строки с `<` после статуса — **заголовки ответа** (`content-type`, `date`, `server`);
- Далее идёт **тело ответа** (JSON от httpbin с данными запроса).
- `httpbin.org/status/404` — сервер вернул только статус `404 NOT FOUND` без тела; `curl` завершился с кодом 0, но флаг `-v` показывает статус. `httpbin.org/status/500` — `500 INTERNAL SERVER ERROR`. Это показывает, что тело ответа необязательно, а клиент должен обрабатывать и ошибочные статусы.

## Задание 7: Простой HTTP-сервер

```bash
python -m http.server 8000
```

- Сервер запущен, `http://localhost:8000` открывается в браузере и показывает листинг директории.
- Создан `index.html` — отображается вместо листинга.
- Сервер останавливается по Ctrl+C.
- Запуск на порту 80 может не работать без прав администратора: порты ниже 1024 — привилегированные (на Linux/macOS; на Windows часто мешают занятые системой порты или недостаток прав).

## Задание 8: Анализ реального сайта

Проанализирован сайт `github.com` через DevTools → Network:
- Первый запрос: `GET https://github.com/` — статус **200**, `Content-Type: text/html; charset=utf-8`, размер документа ~500 КБ.
- Следом идёт десятки запросов к статике: `assets.github.com` (CSS `text/css`, JS `application/javascript`, шрифты `font/woff2`, изображения `image/svg+xml`, `image/png`).
- Запросы к API (например, `https://api.github.com/...`) возвращают `application/json; charset=utf-8`.

```bash
curl -s https://api.github.com/users/lexforfree | head
```

- Waterfall: самые долгие запросы — крупные JS-бандлы; повторные ресурсы отдаются из дискового кэша (статус `304 Not Modified` или `(disk cache)`).

### Задание 1: Анализ config.yaml

1. Сервер работает на порту **8080**.
2. **SSL включён** (`ssl.enabled: true`).
3. Пул соединений с БД: минимум 5, максимум **20** (итого размер пула 5–20).
4. Включены функции: `authentication`, `logging`, `caching`.

### Задание 2: Чтение docker-compose.yml

1. Сервисы: `web` (nginx), `app` (сборка из ./app), `db` (PostgreSQL 15), `redis` (Redis 7).
2. С хоста доступен только `web` на порту **8080** (внутренний 80); `db` и `redis` порты наружу не проброшены.
3. Переменные окружения для `app`: `DATABASE_URL=postgresql://user:secret@db:5432/mydb`, `REDIS_URL=redis://redis:6379`.
4. Данные PostgreSQL хранятся в named volume `pgdata` (`/var/lib/postgresql/data`).
5. В `web` монтируются `./html` (статика) и `./nginx.conf` (read-only).
6. Порядок запуска: сначала `db` и `redis` (от них зависит `app`), затем `app` (от него зависит `web`); `depends_on` гарантирует только порядок старта, не готовность сервиса.

### Задание 8: Диагностика

1. `docker ps -a` — посмотреть, в каком состоянии контейнер (Up / Exited / Restarting) и его код выхода.
2. `docker logs <id>` — искать traceback / сообщения об ошибке (например, неверная переменная окружения).
3. `docker exec -it <id> bash` — войти внутрь и проверить файлы, попробовать запустить процесс вручную.
4. `env` — сверить переменные окружения с ожидаемыми (нет ли опечатки в имени переменной).
5. `netstat -tlnp` — убедиться, что приложение слушает ожидаемый порт внутри контейнера.
6. `ping db` — проверить доступность БД по имени сервиса (внутренней DNS-сети docker-compose).

### Задание 9: Volumes и данные

1. **Bind mount** — монтирование конкретной папки/файла хоста в контейнер (изменения видны обеим сторонам, путь хоста фиксирован). **Named volume** — том, управляемый Docker (`docker volume`), данные хранятся в служебной директории Docker и переживают пересоздание контейнера.
2. При `docker compose down` контейнеры удаляются, но **named volumes сохраняются**; удаляются только с флагом `-v`.
3. Чтобы сохранить данные — использовать named volume (или bind mount) вне контейнера; данные остаются после `docker rm` / `down`.
4. Список томов: `docker volume ls`.

### Задание 10: Сеть контейнеров

Контейнеры в одном `docker-compose.yml` попадают в общую сеть и общаются **по именам сервисов** (Docker встроенный DNS преобразует имя сервиса в IP контейнера). Например, nginx обращается к `http://api:8000`. Проверка: `docker network inspect <project>_default` — видны подключённые контейнеры и их IP; подключение из одного контейнера к другому — `docker exec -it web sh` и затем `wget -qO- http://api:8000/health`.
