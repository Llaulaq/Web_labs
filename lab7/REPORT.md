## Что сделано

- **Счета и переводы** (`app/repositories/accounts.py`, `app/services/accounts.py`, `app/api/accounts.py`):
  - Таблица `accounts(user_id UNIQUE REFERENCES users, balance CHECK >= 0)`
  - `POST /accounts` — открытие счёта, `GET /accounts/{user_id}` — баланс
  - `POST /accounts/transfer` — перевод в транзакции: `BEGIN IMMEDIATE` → проверка счетов → атомарное списание (`UPDATE ... WHERE balance >= ?`, проверка `rowcount`) → зачисление → `COMMIT`; при любой ошибке `ROLLBACK`
- **Посты и решение N+1** (`app/repositories/posts.py`, `GET /users/{id}/posts`): выборка постов с данными автора одним JOIN-запросом; наивная N+1-версия сохранена рядом для сравнения
- **Индексы**: `idx_posts_author` в схеме БД, демонстрация создания/удаления индекса с `EXPLAIN QUERY PLAN`
- **Бенчмарк** `lab7/benchmark.py`: гонка из 10 потоков × 100 переводов, замер N+1 vs JOIN, планы запросов
- **Тесты** (`tests/integration/test_accounts_api.py`): атомарность, недостаток средств, откат — **42 теста пройдено, покрытие 91%**

## Ответы на задания занятия 9

### Задание 1: Транзакция перевода

Реализовано в `AccountRepository.transfer`. Ключевые моменты: `BEGIN IMMEDIATE` захватывает блокировку записи до COMMIT (другие писатели ждут, читатели по умолчанию не блокируются); списание одним UPDATE с условием `balance >= amount` и проверкой `rowcount` — невозможно уйти в минус даже при гонке; `ROLLBACK` при любом исключении.

### Задание 2: Демонстрация гонки

Классическая гонка «проверил-потом-изменил»: два потока читают `seats = 1`, оба регистрируют, результат `-1`. Схема решена в benchmark.py наоборот — показано, что с блокировкой (`BEGIN IMMEDIATE`) и атомарным `UPDATE ... WHERE balance >= ?` из 1000 конкурентных переводов ровно 1000 проходит, баланс неотрицателен, сумма сохранена. В PostgreSQL аналог — `SELECT ... FOR UPDATE` или атомарный UPDATE с rowcount (задание 4).

### Задание 3: Решение уникальностью

`UNIQUE(user_id)` на accounts: повторное создание счёта → `sqlite3.IntegrityError` → обработано в `AccountService.create` → 409 с понятным сообщением. Аналогично `UNIQUE(user_id, course_id)` для регистраций: дубль пользователя на курсе гарантированно невозможен на уровне БД.

### Задание 4: Атомарный UPDATE против SELECT FOR UPDATE

| Подход | Как работает | Плюсы/минусы |
|--------|--------------|--------------|
| `SELECT FOR UPDATE` | Читаем строку с блокировкой, проверяем в приложении, обновляем | Наглядно; на одну строку — лишний round-trip; риск забыть блокировку |
| Атомарный `UPDATE ... WHERE seats > 0` + `rowcount` | Условие проверки и изменение — одна операция | Неуязвимо для гонки без явных блокировок; код короче; в проекте используется именно он |

Оба подхода удерживают гонку; атомарный UPDATE предпочтительнее для простых счётчиков.

### Задание 5–6: Индексы и EXPLAIN

См. результаты замеров выше. Выводы:
- `email` — уже покрыт автоиндексом `UNIQUE`-ограничения; фильтры по `age` до индекса — полный `SCAN`, после — `SEARCH USING INDEX`.
- Составные индексы строятся под конкретные комбинации фильтров (`name+age`, `active+city`); порядок колонок важен — индекс `(a, b)` работает для фильтра по `a` и по `a+b`, но не для фильтра только по `b`.
- `LIKE '%...%'` (подстрока слева) всегда SCAN — для полнотекстового поиска нужны специальные механизмы (FTS5 в SQLite, trigram-индексы в PostgreSQL).

### N+1

Проблема: запрос списка постов с авторами через цикл порождает 1 + N запросов. Решение — JOIN за один запрос (`list_with_author`). Замер: 40-кратное ускорение уже на 200 постах; на проде с сетевой задержкой эффект куда больше. Генерализованный приём — «жадная» загрузка связанных сущностей (ORM: `selectinload`/`joinedload`).

### Анализ медленных запросов

Подход: логирование запросов с временем выполнения (middleware уже пишет длительность запросов), `EXPLAIN QUERY PLAN` для подозрительных запросов, поиск полных сканов (SCAN) больших таблиц, добавление индексов под реальные паттерны фильтрации (не «на всякий случай» — индексы замедляют запись).

Транзакции с блокировкой записи и атомарные условные UPDATE удерживают целостность денежных операций под конкурентной нагрузкой. Замеры подтверждают: JOIN устраняет N+1 (40x), индексы переводят фильтрацию со SCAN на SEARCH. Покрытие тестами сохранено на 91% (42 теста).
